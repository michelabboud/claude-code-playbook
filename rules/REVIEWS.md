# 3 · Code reviews — rules 3.1–3.5

*Read when a task lands, at a batch boundary, before a milestone or release, and before dispatching any reviewer. What a review may NOT do is in the classification table and rule 7.4 (read, report, never fix); this file is what a review MUST do, who does it, and when. The record is the persisted review with its CONFIRMED / REFUTED / UNVERIFIED header. **This file names roles, never models:** which model fills a tier today is `ROSTER.md`, the one file that names any.*

**Why this shape:** a dual review after every task — one mechanical, one deep — is the right instinct, but on a big project it slows development dramatically. Mechanical reviews are slow; deep reviews are slow *and* expensive; and a review that development sits waiting for is a stall either way. So: development does not wait for a review unless waiting is cheaper than the rework — rule 3.5 says exactly when — and the deep review is batched every 3 to 10 tasks depending on complexity, with the coordinator or the plan's author deciding. At the end, regardless of task count, run the best review available. Split the tiers so expensive reasoning is not spent on overkill. The cost of a review is mostly the reviewer reloading the codebase; batching pays that once. The cost of a *late* review is rework on everything built on top of the defect; dependencies, not counts, bound the batch.

3.1 **Three kinds of review — and a tier that climbs the ladder.** The planner plans in levels (WORKFLOW.md vocabulary) and each level closes with a stronger review than the one below it:

    | Level | What closes it | Review | Who (tiers: `ROSTER.md`) | While it runs, development… | Tag |
    |---|---|---|---|---|---|
    | **task** | one unit of work, rules 6.1–6.2 | mechanical | Standard tier; coordinator validates | never waits | `checkpoint/<VERSION>` |
    | **batch** | 3–10 tasks, boundaries in the plan | deep | Strong tier; coordinator validates, Top tier on request | keeps going, up to the ceiling (rule 3.5) | `gate/<VERSION>` on the tip presented |
    | **milestone** | something real shown working end to end | high deep — deep + plan conformance: the planner re-reads the plan against reality and revises it here | Top tier, dual-blind | waits (rule 3.5) | `gate/<VERSION>` |
    | **phase → release** | the phase's last task, rule 6.3 chain | high deep — the best review, rule 3.4 | Top tier, dual-blind, fed every review below it | waits | `v<VERSION>` — never before it passes |

    Levels collapse when the plan is small; the tier of the level that closes never drops.

    - **Mechanical** — tests and lint actually run, input handling, ignored return values, obvious defects, conformance to the brief. **Per task**, on the Standard tier and never the Fast one (measured — `ROSTER.md`), **never blocks the next task**, findings validated by the **coordinator**, not the planner.
    - **Deep** — architecture, concurrency, security, data paths, whether the code still matches the approved plan. **Per batch** of 3–10 tasks by complexity; the **planner writes the batch boundaries into the plan** so nobody decides them under pressure. On the Strong tier, **pipelined** with development (rules 3.3 and 3.5).
    - **High deep** — everything a deep review does, plus the plan itself re-read against reality. **Per milestone and per release**, on the Top tier, dual-blind, with every finding validated against source. It is a **gate**: a deep review looks for defects, whose cost the ceiling in rule 3.5 bounds; a high deep review may *revise the plan*, and work done past it risks being built against a plan that is about to change — no ceiling bounds that.

3.2 **A batch closes at whichever comes first:** (a) the next task would build on unreviewed work it cannot cheaply undo; (b) the diff has outgrown what one reviewer can hold — the human-review literature puts the cliff at a few hundred changed lines, and models dilute the same way, only later; (c) the planner's cap. **Risk overrides cadence:** security, concurrency, data safety, unsafe code, and public-API tasks get the deep review at task grain, always — the cadence rule never undoes rule 8.1's list.

3.3 **Pipelined, never fire-and-forget.** Review batch N while batch N+1 builds. Every finding pins the commit it was found on and is **re-checked against the current tip** before anyone acts on it. A blocker finding **stops the line** — no further dispatch on top of it until it is ruled. "Non-blocking" without the stop is building on known-bad foundations for a day.

    **How to pipeline, concretely** — each line is a way the pipeline fails *silently* if you skip it:

    - **A review's input is a commit, never a working tree.** Commit the work, dispatch the reviewer against that sha, and start the next task at once. Never wait, never poll; the harness notifies on completion. If the reviewer's input is "the current state of the repo", review and development are one process and one of them must wait. The commonest failure is pipelining the dispatch and then waiting for the result anyway, because the review feels important: the pipeline's shape with none of its benefit.
    - **The brief says: read git objects only — `git show <sha>:<path>`, `git diff <a>..<b>`, `git ls-tree`, `git grep <pattern> <sha>` — and never the working tree, because other lanes are using it.** A reviewer that reads the working tree sees the half-written next task and reports defects that do not exist in what it was asked to review. A reviewer that must **build or run tests** does it in a **detached worktree of that sha, in its own scratch directory, with its own build-output directory** — never in the shared tree. That costs disk and a cold build; sharing the build directory instead makes it contend for locks with the lane that is developing.
    - **The brief defines what counts as blocking**, or "non-blocking" means nothing. *Blocking:* a behaviour change nobody asked for, a lost safeguard or cleanup, a weakened limit, a security or data decision reachable a new way, or any defect the next tasks will build on. *Minor:* documentation or comments that misdescribe the code — nothing that changes behaviour. *Informational:* everything else. Blocking stops the line; the other two queue.
    - **The coordinator commits the reviewer's output the moment its findings are complete** — the coordinator, never the reviewer (a review is read-only), staging **that one path and nothing else**, because the working tree holds someone's half-written task. The record is then provably the reviewed version, not whatever the file became later.
    - **In-process subagents of one session do not count as blind** — not to each other, and not to the session that spawned them. Context has been observed crossing that boundary in both directions with neither side composing a read; whatever the mechanism, no brief, path exclusion or directory layout controls it. The second reviewer of a dual-blind pair is a **separate process**. Each blind reviewer writes a **cold-read note to disk before it opens anything else**, and only the findings in that note count as independent corroboration; whatever it adds later is an ordinary finding. Enumerate the excluded paths rather than describing them, and give each reviewer a scratch directory with no other reviewer and no programme material anywhere above it.

3.4 **The release gate gets the best review, regardless of task count.** High deep: the Top tier, dual-blind, given the plan and every batch review as inputs, diving on the risk-class files rather than reading the whole diff cold. Every finding is validated against source before it reaches me. No `v*` tag before it passes (rule 6.3).

3.5 **How far development may run ahead of review.** The test is never what the review costs; it is what being wrong costs. A mechanical finding is local — fixing it three tasks later costs what fixing it now would — so mechanical review has no limit of its own. A deep finding is structural, and its fix grows with everything built on top of it, so deep review has one:

    - **The ceiling is two.** A line of work may carry at most **two unruled batches** under its tip. One is the normal state: batch N is in review while batch N+1 builds. Starting batch N+2 while N is still unruled is allowed and **announced loudly**, because it means the review lane is in trouble — a slow reviewer, an exhausted allowance, a dead lane — and the point of the second slot is that a review outage does not become a development outage. A third never starts: development waits, or moves to work outside the chain. *Ruled* means every finding validated and every blocker fixed or dismissed with a reason. The exposure is the ceiling multiplied by the batch size, so **the planner runs smaller batches whenever two are outstanding** — batch size is the real knob.
    - **Counted per line of work, by ancestry.** A line's count is the number of unruled batches **reachable from its tip** — a question git answers, because a batch is a range of commits. Independent branches and worktrees never affect each other's count. A branch started from unreviewed work **inherits** that work's unruled batches. A **merge adds** the two counts, and a merge that would take the target line over the ceiling **waits** — otherwise fanning out into worktrees and merging back is a way around the ceiling. A reviewer's detached worktree holds no development and counts for nothing.
    - **Three waits hold at any depth:** (1) the next work builds on the unreviewed batch in a way that is expensive to undo — a storage schema, a public API, a protocol — and then only the *dependent* tasks wait; (2) anything irreversible or outward-facing — a migration on real data, a publish, a deploy, a release tag — never runs ahead of its review; (3) a blocker in any outstanding batch stops everything built on top of it (rule 3.3).
    - **High deep reviews are gates.** Every outstanding deep review is ruled before one starts, because it takes them as inputs — so **the count drains to zero at every milestone**, and unreviewed work never survives past one. **The wait has work to do:** the queued minor findings, the backlog, test hardening and docs depend on nothing the review might change.
    - **The planner owns the stall.** If everything in batch N+1 depends on batch N, no review rule can keep development moving — the plan forced the wait. The planner puts independent work after every batch boundary, and puts risk-class tasks *early* in a batch, so their task-grain deep review finishes while the rest of the batch builds.
    - **Review capacity is shared even though the counts are not.** Every line draws on the same reviewers, the same token allowance and the same host; rule 8.1's concurrency cap governs how many reviews run at once. When the review lane is down, every line reaches its ceiling together — report that once, as one fact, not once per line.

**Dual review, and why it must be decorrelated.** Two reviewers are worth more than one only if they can fail differently. Run them **blind to each other** — each assesses independently, and they compare afterwards; blind means separate processes and a cold-read note first (rule 3.3). Where your setup offers more than one model family, put the second pass on a different one (`ROSTER.md`, second-family column); two instances of the same model share the same blind spots, and agreeing with yourself is not corroboration. A review that corrects a review can itself be wrong, so disagreement between reviewers is a finding to verify and rule on, never to average.

**Mechanics that do not change:** a review is read-only (classification table); defects found are fixed in their own commit after the review or deferred loudly (rule 7.4); reviewer ≠ worker; reviewers assess independently before they compare.

**A note on dependent work.** If your coordinator gates a dependent task on an *accepted* prerequisite, and accepted means reviewed, that forbids batching a dependent chain — and pipelining one. Either give the coordinator a provisional state — checks passed, review pending — or declare in the plan that a batch may span dependents. Until one of those exists, batching and pipelining cover independent tasks only.

**Measured, not assumed:** record in the close-out the tokens per review, the defects found per review, and **how often a line reached the ceiling** — so the 3–10 window and the ceiling of two get numbers behind them rather than preferences. A ceiling that is never reached does not matter; one that is reached often means the review lane needs fixing, not the ceiling raising.
